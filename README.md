## How this fork was made

Upstream ([testyourmine/cvaos](https://github.com/testyourmine/cvaos), MIT) provided the
project structure, build system, data extraction and the first ~12 % of the
decompilation (37 C files). Its commit history is preserved here.

Everything after that – the rest of the decompilation and all naming – was produced by
**AI coding agents (Claude by Anthropic, Codex by OpenAI)**, directed and reviewed by a
human maintainer.

**The code is verified, the names are not.** Every change was checked by a full rebuild
and byte-for-byte comparison, which proves the machine code is identical – not that a
name or comment describes the game correctly. Corrections are very welcome.

## Known limitations

- **`FAKEMATCH`** – 223 lines force the compiler's output (`register ... asm("rN")`
  pins, empty `asm("")`, one-shot `do { } while (0)` and `volatile` reads). The original
  code did not contain them; each is marked `/* FAKEMATCH: reason */` and was tested
  to be necessary.
- **Placeholder names** – earlier versions of this README reported "functions
  named 100 % (3,842 / 3,842)". That count included assembly labels of the sound
  engine and libgcc (`_080D86D6`, `Loop1` …) and treated every name without a
  `sub_` prefix as named. The current numbers cover only the 3,417 functions
  compiled from C and count a name as descriptive only when it says what the
  function or its object is. Only 4 names still fall short
  (`Effect_SpawnParticleAnim0/11/12/13`: the number is the animation in the
  shared effect graphics, which has not been looked at). Room objects are identified from the rooms that place
  them (read from the room tables of the ROM) together with their documented
  behaviour, event scenes from the dialogue text they open and the room that
  places them; such names are inferred, not confirmed by the developers. Unidentified names are
  kept as numbers, because a wrong name is worse than a number.
- **Matching-driven style** – some functions use `goto`, odd temporaries or casts to
  reproduce the original instruction order. Where the original code read the same
  bytes both signed and unsigned, two structures describe them (e.g. `MenuListWork` /
  `MenuListUWork`); four file-local views remain (`CameraXView`, `Object13ArmView`,
  `SingleSpriteOamView`, `SoulTypeIcons`).
- **Entity work area** – the per-entity area `0x4F4` … `0x50F` is a
  `union EntityWork` with one structure per entity type
  (`include/structs/entity_work.h`). The split is reconstructed from usage; a few
  views that a nested union cannot express remain as accessor macros. 24 lines
  still go through the raw offset view: generic helpers, entities whose type is
  not known yet, and blocks that extend past the work area.
- **File layout** – sources live in `src/enemy/`, `src/object/`, `src/soul/`,
  `src/player/`, `src/engine/`, `src/menu/`, `src/mode/`, `src/event/` and
  `src/debug/`, each file a consecutive ROM range in its original order. File
  names describe the content (`doors`, `breakables`, `area_props`,
  `scenes_story`, `debug_event_menu` …); no file is named after an address or a
  table index any more. A file holding several unrelated objects or scenes is
  named after the main ones and lists the rest in its header comment – splitting
  it would change the order of code in the ROM. 9 small
  files are still split off only for build reasons: 6 single functions that
  match only with an optimisation pass disabled (`palette_state`,
  `hit_shared_history`, `equipment_list_update`,
  `bestiary_cursor`, `spinning_blade_create`, `box_collision`) – the
  flag would change their neighbours' code; `scene_ending_transformation` (own data
  section); `kyoma_demon_attack` and `tsuchinoko`, cut off from their family because
  the family's flag changes their code. The 4 ARM units (`*_arm.c`, IWRAM code
  built with the ARM compiler) are separate by design.
- **Declarations** – a function used by other files is declared in the header of
  its module (`include/<module>.h`, e.g. `src/engine/entity_common.c` →
  `include/entity_common.h`). Some original files evidently called a function
  without a prototype (implicit `int`): they use the full return register and pass
  unconverted arguments. The header keeps the definition's real types and, next
  to them, declares a second name for the same symbol with `int`-wide types, e.g.
  `extern s32 Entity_LoadGraphicsWide(...) asm("Entity_LoadGraphics");` – no code,
  only another C prototype; those files call the `...Wide` name. 22 functions have
  such an alias. Where the wide callers are the majority (e.g. `Target_IsInRect`),
  the definition itself takes `s32` and narrows on entry (`u16 left = left_;`),
  which the callee did anyway; a caller compiled with a narrower type then carries
  an explicit cast (e.g. `Entity_ShowDamage(entity, (s16)damage, 0)`). 12
  functions are still declared locally by some callers (17 declarations), mostly
  with argument types that no header describes; a comment explains such a
  declaration where the reason is known. Callers
  that use their own view of a shared structure pass it with an explicit pointer
  cast. ROM data used from C is declared in `include/data/<data file>.h` (one
  header per `asm/data/` file, in address order, together with the structures
  that describe the tables); 18 tables are still declared locally – 12 because
  different files read them through different types (e.g. `u8[]` vs. a
  structure), 6 because their element type is defined differently in different
  C files.

## Building

Tested on Linux (Debian under WSL 2).

Requirements: [agbcc](https://github.com/jiangzhengwenjz/agbcc),
`binutils-arm-none-eabi`, `make`, `g++`, `python3`, `git`, and your own ROM dump saved
as `cvaos_us_baserom.gba` in the repository root.

```sh
sudo apt install binutils-arm-none-eabi make g++ python3 git

git clone https://github.com/jiangzhengwenjz/agbcc
cd agbcc && ./build.sh && ./install.sh path/to/cvaos-decomp
cd path/to/cvaos-decomp
(cd tools/preproc && make)

make extract     # once: extracts data from your baserom into data/
make -j          # builds cvaos_us.gba
make check       # verifies the SHA-1
```

See also [INSTALL.md](INSTALL.md).

## Repository layout

| Path | Contents |
|---|---|
| `src/` | decompiled C (game, `m4a` sound engine, GBA library) |
| `include/` | headers: structures, registers, constants; one header per module with the functions other files use; shared `static inline` helpers (`math_inline.h`, `entity_inline.h`, `player_physics.h`, …); `include/data/` declares the ROM data |
| `asm/` | remaining assembly; `asm/data/` holds only `.incbin` references into your baserom |
| `sound/` | song and music player tables (structure only) |
| `tools/` | build tools (`preproc`, `gbafix`, data extractor) |
| `linker.ld` | order of code and data in the ROM |
